# Deploy Change Playbook

## 적용 시점

Dockerfile·docker-compose(3종) 변경, 포트/바인딩 변경, 리소스 캡 조정,
배포 토폴로지 변경.

## 먼저 읽기

- [deployment.md](../deployment.md) — compose 3종 비교, 보안 체크리스트
- [operations.md](../operations.md) — 백업/복구 (배포 변경이 백업 경로를 건드릴 수 있다)
- ADR-009 — Oracle 이전의 제약 (동거 서비스, CPU 캡, 127.0.0.1 바인딩)

## 절차

1. **3종 비교 확인**: 어느 compose(local/기본/oracle)를 바꾸는지, 나머지 2종에도
   같은 변경이 필요한지 판단한다 — 3종의 차이는 의도된 것이니 deployment.md의
   비교표와 대조.
2. **보안 경계 유지**: `MAIA_API_KEY` 필수 치환(`${MAIA_API_KEY:?...}`) 유지 —
   fail-open(H1)에서 이 한 줄이 마지막 방어선이다. 원격 배포는 `127.0.0.1` 바인딩 +
   터널 접근, Qdrant는 내부 네트워크 전용.
3. **리소스 캡 보존**: 동거 서비스 보호용 캡(cpu_shares, mem_limit)은 의도된
   설계다 — 성능 문제의 해법으로 캡 상향을 먼저 꺼내지 않는다 (선례: 임베딩 중복
   로드 OOM은 코드로 해결).
4. **이미지 버전 고정**: `latest` 태그 금지 (M5). 갱신은 의도적 버전 변경으로만.
5. **백업 영향 확인**: 볼륨·경로가 바뀌면 백업/복구 절차(operations.md)도 함께.
6. **문서 갱신**: deployment.md (+ 운영 절차 변경 시 operations.md).

## 체크리스트

- [ ] `MAIA_API_KEY` 필수 치환이 유지되는가?
- [ ] 원격 노출 시 인증 없는 포트가 없는가? (Qdrant 포함)
- [ ] 이미지 태그가 버전 고정인가?
- [ ] 리소스 캡이 보존되는가? (변경했다면 동거 서비스 영향 근거는?)
- [ ] 백업/복구 절차가 여전히 유효한가?
- [ ] 개인 배포 비밀(도메인 계정·크리덴셜 경로)을 커밋하지 않았는가? — 공개 레포
- [ ] deployment.md 갱신 (같은 커밋)
