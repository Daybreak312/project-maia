# Phase 3: Search Agent — 검색 지능

> **Goal:** 검색을 1회성 조회에서, 충분해질 때까지 스스로 각도를 바꿔 탐색하는 능동 프로세스로 바꾼다.
> **Prerequisite:** Phase 2 (그래프 + Ingest Agent)
> **Output:** deep search 파이프라인 (API + MCP) + 검색 로그

---

## 1. Purpose (목적)

에이전트가 Maia에게 "A회사 관련 모든 것"을 물을 때 지금은 상위 5개 문서가 전부다. 인공두뇌라면 연상해야 한다: 초기 결과에서 그래프를 따라가고, 부족하면 질문을 바꿔 다시 찾고, 모은 것을 정리해 내놓는다. 이 phase는 Maia의 "회상(recall)" 능력이다.

## 2. Goals (목표)

1. Search Agent가 결과 충분성을 평가하고 부족하면 쿼리를 재작성해 재탐색한다 (상한 내).
2. 초기 결과의 그래프 이웃으로 탐색을 확장한다.
3. 멀티 라운드 결과를 중복 제거·재정렬해 합성한다.
4. 기존 검색은 그대로 유지된다 — agent 검색은 opt-in.
5. 모든 검색이 로그로 남아 Phase 5의 거버넌스 신호가 된다.

## 3. Acceptance Criteria (달성 조건)

- [ ] agent 모드 검색이 기존 모드보다 넓은 관련 문서 집합을 반환하는 시나리오 테스트가 존재한다 (mock provider로 재작성·확장 경로 검증).
- [ ] 재작성 루프가 상한(최대 3회)에서 반드시 멈춘다.
- [ ] LLM 실패 시 초기 hybrid 검색 결과가 그대로 반환된다 (에러가 아니라 결과 + 폴백 표시).
- [ ] 응답에 탐색 과정 요약(라운드 수, 사용된 쿼리들, 그래프 확장 여부)이 포함된다.
- [ ] 결과에 중복 문서가 없고, 점수 기준 정렬이 유지된다.
- [ ] `deep_search` MCP tool이 동작한다.
- [ ] 검색 로그(쿼리, 모드, 결과 수, 최고 점수, zero-result 여부, 소요 시간)가 워크스페이스별로 축적된다.

## 4. Anti-Goals (하면 안 되는 것)

- 답변 생성(RAG 응답 합성) — Maia는 문맥을 반환한다. 답변은 호출한 에이전트의 몫.
- 웹 검색 등 외부 소스 폴백 — 내부 지식 탐색만. (외부 유입은 Phase 4 커넥터의 영역)
- 검색 캐싱/성능 최적화 — 정확성 우선, 최적화는 측정 후.
- 재작성 쿼리의 사용자 노출 UI — 응답 메타데이터면 충분.

## 5. User Scenarios

1. **클러스터 회상**: OpenClaw 에이전트가 deep_search("이사 관련 전부")를 호출한다. 초기 검색 3건 → 이웃 확장으로 계약·가구·주소변경 문서 5건 추가 → 재작성("전입신고")으로 2건 추가 → 중복 제거 후 관계 요약과 함께 반환.
2. **부족 인지**: "양자컴퓨터 공부 기록" 검색에 결과가 0건이면, 재작성을 시도하고 그래도 없으면 "관련 지식 없음 + 시도한 쿼리들"을 반환한다 (거짓 결과를 만들지 않는다).
3. **폴백**: LLM 장애 중 agent 검색을 호출해도 기존 hybrid 결과가 폴백 표시와 함께 온다.
4. **관측**: 소유자가 나중에 검색 로그에서 zero-result 쿼리들을 보고 지식 공백을 파악한다 (Phase 5에서 자동화).

## 6. Functional Requirements

- agent 검색은 기존 검색 API의 opt-in 파라미터로 활성화된다. 기본값은 기존 동작.
- 파이프라인: 초기 hybrid 검색 → 충분성 평가(LLM) → [부족 시] 쿼리 재작성 재검색 (최대 3회) → [엔트리 존재 시] 그래프 이웃 확장 (depth는 워크스페이스 설정) → 합성(중복 제거, 재정렬, 상위 N 절사).
- 충분성 평가와 재작성은 LlmProvider 경유, 프롬프트 중앙화.
- 확장으로 추가된 문서는 유래(어느 문서의 이웃인지)가 표시된다.
- 검색 로그는 파일 기반 append 저장, 로그 실패가 검색을 실패시키지 않는다.
- 교차 워크스페이스 검색과 조합 가능해야 한다 (Phase 1 기능 위에서 동작).

## 7. Data Requirements

- agent 검색 응답: 기존 결과 형식 + 라운드 수, 시도 쿼리 목록, 확장 출처, 폴백 여부.
- 검색 로그 레코드: 시각, 워크스페이스, 쿼리, 모드, 결과 수, 최고 점수, zero-result 여부, 소요 시간, (agent 모드 시) 라운드 수.

## 8. Constraints & Invariants

- 입력당 LLM 호출 상한: 충분성 평가 + 재작성 합쳐 5회 이하.
- 전체 파이프라인 시간 상한 존재 (초과 시 그 시점까지의 결과 반환).
- 동일 쿼리 재검색 금지 (재작성 결과가 이전과 같으면 루프 종료).
- 결과 총량 상한 — 확장이 결과를 무한히 불리지 않는다.

## 9. Architecture Decision Points

| Decision | User's Choice | Notes |
|----------|--------------|-------|
| 충분성 평가 프롬프트/기준 | 자율 | 보수적으로 — 과잉 탐색보다 조기 종료 선호 |
| 합성 시 재정렬 방식 | 자율 | RRF 재사용 또는 점수 기반, 근거 기록 |
| 로그 파일 형식/로테이션 | 자율 | 파일 기반, 일 단위 롤업 가능 구조 권장 |
| 시간 상한 값 | 자율 | 워크스페이스 설정 노출 권장 |

## 10. Risks & Mitigations

- **리스크**: agent 검색이 느려 에이전트 UX 저하 → 시간 상한 + 부분 결과 반환. 기존 검색은 그대로라 선택지 존재.
- **리스크**: 재작성이 의미를 벗어나 무관한 결과 혼입 → 합성 단계에서 원 쿼리와의 유사도로 절사, 확장 유래 표시로 관측 가능.
- **리스크**: 로그 파일 무한 성장 → 일 단위 파일 분리.
