# Phase 5: Patrol — 자기 관리 & 메모리 거버넌스

> **Goal:** 두뇌가 스스로의 기억 상태를 점검하게 한다 — 수정은 하지 않고, 후보를 찾아 사람의 판단을 받는다.
> **Prerequisite:** Phase 2 (그래프), Phase 3 (검색 로그), Phase 4 (커넥터 신호)
> **Output:** Patrol 에이전트 + Review Queue (API/UI) + 메트릭 롤업

---

## 1. Purpose (목적)

기억은 부패한다 — 오래되고, 중복되고, 고립되고, 현실과 어긋난다. 완전 자동 수정은 자기참조 순환(RAG로 RAG 검증)과 오탐 피로를 낳으므로, Maia의 원칙은 **반자율**이다: 시스템이 후보를 식별해 플래그를 세우고, 소유자가 판단하고, 그 피드백이 축적된다. Patrol은 청소부가 아니라 관측·거버넌스 계층이다.

## 2. Goals (목표)

1. Patrol이 주기 실행되어 staleness/중복/고아/외부 불일치 후보를 Review Queue에 쌓는다.
2. 판단이 필요 없는 수학적 유지보수(엣지 시간 감쇠 재계산)는 자동 수행한다.
3. Review Queue를 API와 UI로 처리할 수 있고, 판단 결과가 문서에 반영된다.
4. 검색 피드백(관련 없음)이 수집된다.
5. 메트릭(검색 품질, 그래프 헬스, 유입 통계)이 일 단위로 롤업되어 조회 가능하다.

## 3. Acceptance Criteria (달성 조건)

- [ ] Patrol 실행 후 각 탐지 유형별 항목이 Review Queue에 사유와 함께 쌓인다 (동일 문서·동일 사유 중복 플래그 없음).
- [ ] Review Queue 항목에 유효/수정 필요/삭제 판단을 제출하면 상태가 반영된다: 유효 → freshness 갱신 + 플래그 해제, 삭제 → 문서 삭제.
- [ ] 엣지 가중치 시간 감쇠가 Patrol 실행 시 자동 재계산된다.
- [ ] 검색 결과에 대한 "관련 없음" 피드백이 API로 수집·저장된다.
- [ ] 일 단위 메트릭 롤업이 생성되고 API로 조회된다 (검색 zero-result율, 그래프 노드/엣지/고아 수, 유입 전략 분포 포함).
- [ ] Patrol 실행이 수동 트리거로도 가능하고, 실행 이력(시각, 탐지 수)이 남는다.
- [ ] Review Queue 대시보드 UI에서 항목 확인·판단이 가능하다.

## 4. Anti-Goals (하면 안 되는 것)

- 자동 삭제/자동 병합 — 어떤 경우에도 사람 판단 없이 문서를 파괴하지 않는다.
- 피드백 기반 ML 학습 — 피드백은 저장·집계까지만. 탐지 정확도 자동 개선은 장기 과제.
- 알림 발송(이메일/디스코드 등) — 큐에 쌓는 것까지가 Maia의 책임. 알림은 소비자(에이전트)의 몫.
- 그래프 시각화 페이지 — 백로그 유지. 메트릭은 수치 API + 간단한 수치 대시보드까지.

## 5. User Scenarios

1. **아침 점검**: Patrol이 새벽에 돌고, 소유자(또는 관리 에이전트)가 Review Queue에서 "6개월 전 이직 준비 문서 — stale 후보"를 보고 "아직 유효"를 누른다. 문서 freshness가 갱신되고 당분간 다시 플래그되지 않는다.
2. **중복 정리**: 유사도 높은 문서 쌍이 병합 후보로 올라온다. 소유자가 확인 후 한쪽을 삭제한다.
3. **외부 불일치**: 커넥터 소스 파일은 갱신됐는데 연결 문서가 오래됐으면 불일치 후보로 플래그된다.
4. **지식 공백 인지**: 메트릭에서 zero-result 쿼리 빈발 주제를 보고 소유자가 해당 지식을 채워 넣는다.
5. **자동 유지보수**: 오래된 엣지의 가중치가 감쇠 곡선에 따라 자동으로 낮아져, 검색 그래프 확장에서 자연히 뒤로 밀린다.

## 6. Functional Requirements

### Patrol 에이전트
- 탐지기: (a) staleness — 나이 + 검색 미적중 기간 기준, (b) 중복 — 유사도 상위 쌍, (c) 고아 — 엣지 없는 문서, (d) 외부 불일치 — 커넥터 소스 수정 시각 vs 문서 갱신 시각.
- 각 탐지기는 독립 실행되고 하나의 실패가 다른 탐지기를 막지 않는다.
- 탐지 결과는 Review Queue에 항목으로 추가된다 (문서 ID, 유형, 사유, 근거 데이터, 시각).
- 이미 열린 동일 항목(같은 문서+유형)은 중복 생성하지 않는다.
- "유효" 판단된 문서는 freshness 기준점이 갱신되어 유예된다.
- 엣지 감쇠 재계산은 탐지와 별개의 자동 단계로 실행.
- 실행 주기는 워크스페이스 patrol 설정을 따르고, 수동 트리거 API가 있다.
- 탐지 임계값(나이, 유사도 등)은 워크스페이스 patrol 설정(strictness 포함)에서 파생된다.

### Review Queue
- 항목 상태: 대기 → 판단됨(유효/수정 필요/삭제됨) / 기각.
- 조회(필터: 상태·유형), 판단 제출, 일괄 판단.
- 판단 이력이 보존된다 (누가/언제 — 단일 사용자라도 시각과 판단 기록).

### 피드백
- 검색 응답의 문서에 대해 "관련 없음" 피드백 제출 API. 저장: 쿼리, 문서 ID, 시각.
- 피드백은 staleness 탐지기의 입력 신호로 사용 가능해야 한다 (구조만 — 가중 로직은 단순해도 됨).

### 메트릭
- 일 단위 롤업 생성 (Patrol 실행 시 또는 스케줄): 검색(횟수, zero-result율, 평균 점수), 그래프(노드/엣지/고아/평균 degree), 유입(전략 분포, 문서 수), Patrol(탐지 수, 처리율).
- 롤업 조회 API (기간 지정).
- Frontend: Review Queue 대시보드 (목록, 사유, 판단 버튼) + 메트릭 요약 카드.

## 7. Data Requirements

- ReviewItem: 항목 ID, 워크스페이스, 문서 ID, 유형, 사유 텍스트, 근거(수치), 상태, 생성·판단 시각.
- 피드백 레코드: 쿼리, 문서 ID, 유형(관련 없음), 시각.
- 메트릭 롤업: 일자 키, 영역별 수치 집합.
- 문서 freshness 기준점: "유효" 판단 시각.

## 8. Constraints & Invariants

- Patrol은 읽기 + 플래그 + 감쇠 재계산만 한다. 문서 내용을 변경하거나 삭제하지 않는다.
- Patrol 실행이 검색/유입 성능에 주는 영향 최소화 (백그라운드, 배치 처리).
- Review Queue 판단은 멱등 — 같은 판단 재제출이 상태를 깨지 않는다.
- 탐지기는 LLM 없이 신호(수치) 기반으로 동작한다 — LLM 판단은 이 phase 범위 밖 (비용·오탐 제어).

## 9. Architecture Decision Points

| Decision | User's Choice | Notes |
|----------|--------------|-------|
| staleness 점수식 | 자율 | strictness 설정 반영, 근거를 항목에 기록 |
| 큐/메트릭 저장 형식 | 자율 | 파일 기반 유지 |
| 감쇠 곡선 | 자율 | Phase 2의 lambda 재사용 권장 |
| 대시보드 구성 | 자율 | 기능 우선, 수치 카드 수준 |

## 10. Risks & Mitigations

- **리스크**: 오탐 폭주로 큐가 쓰레기장이 됨 → 유형별 일일 생성 상한 + strictness 기본값 보수적으로.
- **리스크**: 삭제 판단 실수 → 삭제는 soft-delete(버전 보관 활용) 또는 확인 단계 — 파괴 전 복구 가능성 보장.
- **리스크**: 메트릭 수집이 핵심 경로를 느리게 함 → 기존 로그(Phase 3) 재활용, 롤업은 배치.

## Notes

이 phase가 끝나면 Maia는 "저장하고, 연결하고, 회상하고, 흘러들어오고, 스스로 점검하는" 완결 루프를 갖춘다. 이후는 운영(실데이터 적재, OpenClaw 연동 상시화)과 백로그(시각화, 외부 커넥터)의 영역이다.
